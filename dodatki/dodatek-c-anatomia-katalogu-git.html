Anatomia katalogu .git

Co naprawdę leży w .git: obiekty, refy, HEAD, packfile. Zwiedzanie z cat-file w ręku, na jednorazowym repozytorium.

Wycieczka

Co leży w katalogu .git

Wszystko, co ta książka opisuje jako model, jest w tym katalogu widoczne gołym okiem. Warto raz przejść się po nim z komendami w ręku — najlepiej w jednorazowym repozytorium, założonym specjalnie na tę okazję.

ls .gitświeże repozytorium z dwoma commitami
ls .git
COMMIT_EDITMSG   config      hooks    info    logs
HEAD             description index    objects refs
PozycjaCo to jest
objects/wszystkie obiekty: commity, drzewa, blob-y. Jedyne miejsce z treścią
refs/gałęzie, tagi i refy zdalne — pliki po 41 bajtów
HEADwskaźnik na bieżącą gałąź (Rozdział 4)
indexplik binarny z zawartością indeksu (Rozdział 1)
logs/reflog: historia wartości refów (Rozdział 18)
configkonfiguracja tego repozytorium
hooks/lokalne hooki, domyślnie same przykłady (Rozdział 20)

Siedem pozycji. Nie ma tu żadnej bazy danych ani dziennika transakcji.

Obiekty

Adres jest ścieżką

Katalog objects wygląda dziwnie, dopóki nie zauważy się reguły: nazwa podkatalogu to dwa pierwsze znaki skrótu, a nazwa pliku — pozostałe trzydzieści osiem.

objectsadres zamieniony na ścieżkę
ls .git/objects
05  2b  91  b9  ce  d6  ec  info

git rev-parse HEAD
b9c30732f303dcf5cf4bd526da67b6da07118ca6

# ten sam obiekt jako plik:
.git/objects/b9/c30732f303dcf5cf4bd526da67b6da07118ca6

Podział na dwa znaki istnieje wyłącznie po to, żeby nie trzymać dziesiątek tysięcy plików w jednym katalogu.

Obiekty są skompresowane, więc nie da się ich przeczytać zwykłym poleceniem — od tego jest git cat-file. Przełącznik -t podaje typ, -s rozmiar, -p wypisuje treść:

git cat-filetyp i rozmiar sześciu obiektów
commit  201  b9c3073
commit  160  d63f706
tree     74  2b6f655
tree     37  91e2a2e
blob      9  ec38e55
blob      7  05cbc96

Całe repozytorium z dwoma commitami: sześć obiektów, łącznie niecałe pięćset bajtów.

Zwróć uwagę na rozmiary. Commit to dwieście bajtów, bo zawiera tylko metadane i wskaźniki. Drzewo — kilkadziesiąt, bo to lista wpisów. Cała treść siedzi w blob-ach, a te są dokładnie tak duże, jak pliki, które opisują.

Refy i HEAD

Trzydzieści bajtów, od których wszystko zależy

refs i HEADzwykłe pliki tekstowe
cat .git/HEAD
ref: refs/heads/master

cat .git/refs/heads/master
b9c30732f303dcf5cf4bd526da67b6da07118ca6

cat .git/logs/HEAD
0000000... b9c3073... Ty <ty@example.com> 1788808038 +0200  commit: Dodaj renderer

Trzecia z tych komend pokazuje reflog w postaci surowej. Każda linia to: stara wartość, nowa wartość, autor, czas i opis operacji. Dokładnie to, co wypisuje git reflog, tylko bez upiększeń — i widać tu, że reflog jest zwykłym plikiem dopisywanym linia po linii.

Jest jeszcze jedno miejsce, w którym warto zajrzeć: .git/packed-refs. Przy większej liczbie gałęzi git przenosi refy z osobnych plików do jednego wspólnego, żeby nie trzymać tysięcy czterdziestobajtowych plików. Jeśli więc ls .git/refs/heads pokazuje mniej gałęzi, niż wypisuje git branch, to właśnie dlatego.

Pakowanie

Dlaczego repozytorium nie puchnie

Skoro każda wersja pliku to osobny blob z pełną treścią, repozytorium powinno rosnąć bardzo szybko. Nie rośnie, bo git co jakiś czas pakuje obiekty: zapisuje je razem w jednym pliku i przechowuje podobne obiekty różnicowo.

Jest to operacja czysto techniczna i całkowicie niewidoczna z poziomu modelu: obiekty nadal mają te same adresy i tę samą treść, zmienia się wyłącznie sposób zapisu na dysku. Uruchamia ją git gc, wołane automatycznie przy niektórych operacjach.

Przy okazji pakowania git usuwa obiekty, do których nic nie prowadzi i którym minął termin z reflogu. To jest ten moment, w którym porzucony commit naprawdę znika — nie w chwili amendu ani resetu.

git count-objects -vHile czego jest
git count-objects -vH
count: 6            # obiekty luzne
size: 24.00 KiB
in-pack: 0          # obiekty w plikach spakowanych
size-pack: 0 bytes

Warto tę komendę znać przy diagnozowaniu repozytoriów, które ważą podejrzanie dużo. Wysoka wartość size-pack przy niewielkim drzewie roboczym oznacza zwykle, że w historii siedzą duże pliki binarne — a te, jak mówi Rozdział 7, zostają tam na zawsze.
