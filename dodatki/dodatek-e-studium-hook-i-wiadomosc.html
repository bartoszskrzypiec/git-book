Studium przypadku: literówka kontra hook serwerowy

Prefiks zgubiony przy wklejaniu, hook pilnujący formatu, i pytanie, dlaczego drugi commit z poprawką niczego nie naprawia.

Sytuacja

Trzy znaki, które nie dojechały

Fikcyjny projekt, fikcyjne zgłoszenie ABC-1234, prawdziwy mechanizm. Zadanie: przenieść pomocniczy skrypt do rangi właściwego narzędzia. Sześć plików, dwa i pół tysiąca linii, testy przechodzą.

Wiadomość commita była przygotowana wcześniej i wklejona ze schowka. Do pola commita dojechała bez pierwszych trzech znaków — zamiast [ABC-1234] Dodaj wyszukiwarke w historii wylądowało odaj wyszukiwarke.

stan po pierwszym commiciei po poprawce
✗ odaj wyszukiwarke
✓ [ABC-1234] Dodaj wyszukiwarke

Push na gałąź funkcyjną przeszedł bez słowa. Problem ujawnił się dopiero przy próbie scalenia — i to jest pierwszy wniosek z tej historii, opisany w Rozdziale 21: gałąź funkcyjna zwykle nie jest sprawdzana, więc informacja zwrotna przychodzi z opóźnieniem.

Dlaczego to blokowało scalenie

Hook patrzy na ref, potem na każdy commit

Format wiadomości pilnuje hook po stronie serwera. Robi dwie rzeczy w tej kolejności: najpierw sprawdza, na jaki ref lecą commity, a potem — tylko jeśli to gałąź chroniona — dopasowuje każdą wiadomość do wzorca wymagającego prefiksu w nawiasach kwadratowych.

OperacjaRef docelowyWynik
push gałęzi funkcyjnejrefs/heads/ABC-1234przeszło — ref nie jest chroniony, hook kończy działanie od razu
scalenie merge requestarefs/heads/masterodrzucone — hook ogląda każdy commit z zakresu

Ten sam commit, dwie różne odpowiedzi. Różni je wyłącznie ref, na który leci.

I tu jest sedno, dla którego nie wystarczył drugi commit z poprawką. Hook waliduje wszystkie commity dochodzące do gałęzi chronionej, a nie stan końcowy gałęzi. Wadliwy commit zostałby w historii i pojechał do gałęzi głównej razem z poprawką — więc scalenie nadal by nie przeszło.

Jedynym wyjściem było przepisanie tego commita, a nie dopisanie czegokolwiek na wierzchu. Mechanizm opisuje Rozdział 21; tutaj widać go w działaniu.

Co zrobił amend

Nowy obiekt, ten sam rodzic

Ponieważ wadliwy commit był ostatni, wystarczył git commit --amend. Warto prześledzić, co dokładnie się przy tym stało.

przed i porodzenstwo, nie nastepstwo
Oba commity mają tego samego rodzica. Żaden nie pochodzi od drugiego — to rodzeństwo.

Amend zrobił przy okazji dwie rzeczy naraz, i warto to odnotować jako dobrą praktykę: podmienił wiadomość i wciągnął do tego samego commita dwie drobne poprawki w kodzie, zauważone przy przeglądzie. Dzięki temu w historii został jeden czysty commit, bez śladu w stylu „popraw literówkę”.

Dlaczego push musiał być wymuszony

Diagnoza jedną komendą

Zwykły push wymaga, żeby wysyłany commit był potomkiem tego z serwera. Nowy commit nie był — miał z nim wspólnego rodzica. Git raportuje to dokładnie tak:

stan po amendziediagnoza i odmowa
git rev-list --left-right --count HEAD...@{upstream}
1       1     ← 1 commit lokalnie, 1 na origin, wspolny rodzic

git push
 ! [rejected]  ABC-1234 -> ABC-1234 (non-fast-forward)

Podpowiedź gita sugeruje w tym miejscu git pull — i byłby to najgorszy możliwy ruch, bo ściągnąłby z powrotem commit z literówką i scalił go z poprawionym. Właściwą odpowiedzią było git push --force-with-lease, opisane w Rozdziale 17.

Wymuszenie było w tym przypadku bezpieczne, bo wszystkie warunki z listy w Rozdziale 17 były spełnione: gałąź funkcyjna, brak otwartego merge requesta, nikt inny na niej nie pracował, a stary commit i tak został w reflogu.

Wnioski

Co z tego zostaje na przyszłość

  • Sprawdź wiadomość zaraz po commicie, zanim zaczniesz robić cokolwiek innego: git log -1 --pretty=%s. Poprawka kosztuje wtedy jeden amend.
  • Dopisanie commita nie naprawia commita. Reguły sprawdzane per commit wymagają przepisania, nie uzupełnienia.
  • Przepisuj przed otwarciem merge requesta, nie po. To ta sama operacja, ale o zupełnie innym koszcie.
  • Lokalny hook wyprzedza serwerowy. Ta sama kontrola u siebie zamienia problem tygodniowy w problem sekundowy.

I jeden wniosek ogólniejszy, który wraca w całej książce: komunikat odmowy mówił o pushu, przyczyna leżała w wiadomości commita, a rozwiązanie polegało na zrozumieniu, że commit jest niezmienny. Trzy różne poziomy, jedna sytuacja — i właśnie dlatego model z pierwszej części jest wart tych pięciu rozdziałów.
