Dodatek H / Głębiej

Dwadzieścia sytuacji i wyjście z każdej

Pełne recepty na to, co zdarza się naprawdę: commit na złej gałęzi, detached HEAD, zgubiona praca, rebase w połowie, nadpisany branch.

Jak korzystać

Recepty, nie wyjaśnienia

Rozdział 30 jest katalogiem objawów i odsyła dalej. Ten dodatek zawiera pełne przepisy: co wpisać, w jakiej kolejności i czego się spodziewać. Wyjaśnienia są w rozdziałach — tutaj są komendy.

Dwie zasady obowiązują we wszystkich dwudziestu przypadkach. Zapisz punkt powrotu (git rev-parse HEAD) i sprawdź katalog roboczy (git status), zanim cokolwiek zrobisz. Pierwsze zamienia każdą naprawę w operację odwracalną, drugie chroni przed jedyną nieodwracalną stratą.

Grupa I

Commit trafił nie tam, gdzie miał

#Sytuacja i recepta
1Zacommitowałem na złej gałęzi.
git switch -c wlasciwa — gałąź powstaje tutaj, z commitem.
git switch zla potem git reset --hard origin/zla — cofa tamtą.
2Zacommitowałem na gałęzi głównej, nic nie wypchnąłem.
Jak wyżej. Nic nie wyjechało, bo push by nie przeszedł (R.22).
3Commit nie zawiera ostatniej poprawki.
git add plik potem git commit --amend --no-edit.
4Chcę podzielić jeden commit na dwa.
git reset --soft HEAD~1, potem git add -p i dwa osobne commity.
5Zły plik wjechał do commita.
git restore --staged --worktree plik po resecie miękkim, albo git rm --cached i amend.
6Potrzebuję jednego commita z cudzej gałęzi.
git cherry-pick <sha> — powstaje kopia (R.19).
Grupa II

Push nie przechodzi

#Sytuacja i recepta
7non-fast-forward, a nikt inny tu nie pracuje.
git status -sb — jeśli „behind” to Twoje commity sprzed amendu: git push --force-with-lease.
8non-fast-forward, ktoś dołożył commity.
git fetch, potem git rebase origin/<galaz>, potem push.
9stale info przy wymuszonym pushu.
git fetch, obejrzyj git log HEAD..origin/<galaz>, dopiero potem decyduj (R.17).
10Hook odrzucił wiadomość ostatniego commita.
git commit --amend -m "[ABC-1234] Poprawny opis", potem wymuszony push.
11Hook odrzucił wiadomość starszego commita.
git rebase -i origin/master, przy tym commicie zmień pick na reword.
12Wypchnąłem coś przez pomyłkę na wspólną gałąź.
git revert <sha> — nigdy reset (R.15).
Grupa III

Coś zniknęło

#Sytuacja i recepta
13Nieudany rebase, chcę stan sprzed.
W trakcie: git rebase --abort. Po zakończeniu: git reset --hard <galaz>@{1}.
14reset --hard wyrzucił commity.
git reflog, znajdź skrót sprzed, git reset --hard <sha>.
15Usunąłem gałąź.
git reflog albo skrót z komunikatu o usunięciu, potem git branch nazwa <sha>.
16Commity zrobione w stanie odczepionym.
Jeśli nadal tam jesteś: git switch -c nazwa. Jeśli już nie: git reflog i to samo na skrócie.
17Reflog nic nie pokazuje.
git fsck --lost-found — wypis obiektów bez refów, potem git show na każdym.

W żadnym z pięciu powyższych przypadków nic nie zostało utracone. Jedyny prawdziwy przypadek straty to zmiana, która nigdy nie stała się commitem — wtedy zostaje git stash list i historia lokalna edytora.

Grupa IV

Stan repozytorium

#Sytuacja i recepta
18Rebase stanął na konflikcie.
Popraw plik, usuń markery, git add plik, git rebase --continue. Wyjście: --abort.
19Plik dalej widoczny mimo .gitignore.
git rm --cached plik i commit. Uprzedź zespół — u nich plik zniknie (R.7).
20Muszę odłożyć pracę na pięć minut.
git stash push -m "opis", potem git stash pop. Nowe pliki wymagają -u.

Warto zauważyć, że we wszystkich dwudziestu przypadkach użyto łącznie kilkunastu komend, a najczęściej powtarza się jedna trójka: reflog, reset, switch -c. To nie przypadek — sprowadzają się one do jednej operacji z Rozdziału 4: przestawienia wskaźnika na właściwy commit.

Jeśli sytuacja, w której jesteś, nie pasuje do żadnej z powyższych, wróć do czterech pytań z Rozdziału 30. Odpowiedź na nie zwykle sprowadza nowy przypadek do jednego z tych dwudziestu.
