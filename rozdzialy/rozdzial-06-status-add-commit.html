Rozdział 6 / Codzienna praca

status, add, commit — i co naprawdę robi add

„Dodaj plik do commita” to złe tłumaczenie. add kopiuje bieżącą treść pliku do indeksu — a to, co zrobisz z plikiem potem, już tam nie trafi.

TL;DR
  • Cykl status → add → commit powtarzasz kilkanaście razy dziennie. Warto go rozumieć jako składanie szkicu, a nie jako zapisywanie pracy.
  • git commit -a pomija index — i pomija też pliki nieśledzone. To wygodny skrót, który przy okazji odbiera możliwość zbudowania częściowego commita.
  • Dobry commit to jedna zmiana z jednym powodem. Nie „koniec dnia”, tylko „coś, co da się opisać jednym zdaniem i wycofać w całości”.
Cykl · trzy komendy i jedna decyzja

Co się dzieje między add a commit

Z Rozdziału 1 wiesz już, że add kopiuje treść do indeksu. Codzienna praca sprowadza się do świadomego korzystania z tego jednego faktu: między zmianą pliku a commitem masz miejsce, w którym decydujesz, co dokładnie ma wejść.

cykl pracygdzie zapada decyzja
Trzeci krok jest jedynym, w którym masz coś do wyboru. Reszta wynika.

Najczęstszy zarzut wobec indeksu brzmi: to zbędny krok, przecież chcę zacommitować wszystko. Git ma na to skrót — git commit -a — który dodaje wszystkie śledzone zmienione pliki i od razu buduje commit. Warto tylko wiedzieć, co przy tym tracisz i o czym łatwo zapomnieć.

Po pierwsze, -a nie obejmuje plików nieśledzonych. Nowy plik, którego nigdy nie dodałeś, zostanie pominięty bez słowa. To najczęstsza przyczyna commita, w którym „brakuje pliku” — a właściwie nigdy go tam nie było.

Po drugie, wszystko wchodzi razem. Jeżeli przy okazji pracy nad jedną rzeczą poprawiłeś przy okazji trzy inne, wylądują w jednym commicie i nie da się ich potem wycofać osobno.

Narzędzie · częściowy commit

add -p, czyli wybieranie fragmentów

Kiedy w jednym pliku masz dwie niezwiązane zmiany, git add -p przechodzi z Tobą przez plik fragment po fragmencie i pyta o każdy: dodać, pominąć, podzielić na mniejsze. Wynikiem jest index zawierający dokładnie to, co chcesz, przy nietkniętym katalogu roboczym.

git add -pnajważniejsze odpowiedzi
y   dodaj ten fragment
n   pomin ten fragment
s   podziel na mniejsze fragmenty
e   edytuj recznie, co dokladnie wchodzi
q   zakoncz, zachowujac dotychczasowe decyzje

Reszta liter jest opisana w podpowiedzi pod znakiem zapytania.

To jest jedno z niewielu miejsc, w których terminal wyraźnie wygrywa z interfejsem graficznym — choć akurat tę operację część IDE też potrafi, pod nazwą w rodzaju „stage selected lines”. Nazwa jest inna, mechanizm identyczny: budujesz index niezależnie od tego, co masz na dysku.

Po takim commicie warto pamiętać o rzeczy, która bywa zaskoczeniem: kod w commicie nigdy nie został uruchomiony w tej postaci. Testowałeś stan z dysku, a zacommitowałeś jego część. Jeśli commit ma przejść przez zautomatyzowaną kontrolę, wypada sprawdzić, czy sam się kompiluje — git stash -k odkłada wszystko poza indeksem i pozwala to zrobić.

Rozmiar commita · pytanie, na które nie ma reguły

Jedna zmiana, jeden powód

Nie ma dobrej odpowiedzi wyrażonej w liczbie linii. Jest natomiast dobre kryterium: czy da się to opisać jednym zdaniem, które nie zawiera słowa „oraz”. Jeśli opis brzmi „dodaj eksport i napraw wczytywanie i popraw literówkę”, to są trzy commity.

Drugie kryterium jest jeszcze bardziej praktyczne: czy dałoby się to wycofać w całości. Commit jest najmniejszą jednostką, którą da się cofnąć jednym revert, przenieść jednym cherry-pick albo wskazać jako winnego przy szukaniu regresji. Jeżeli w środku siedzą dwie niezwiązane rzeczy, każda z tych operacji zaczyna być kompromisem.

Ma to znaczenie także dla wiadomości. Skoro commit ma jeden powód, to opis może mówić dlaczego, a nie co — bo „co” widać w diffie. „Zmień domyślny format zapisu na taki, który czyta starsza wersja narzędzia” jest wart więcej niż „zmiana w konfiguracji”, i to niezależnie od tego, jaki format wiadomości narzuca projekt.

Formaty bywają zresztą narzucone twardo. Wiele zespołów wymaga prefiksu z numerem zgłoszenia, a serwer potrafi odrzucić push z wiadomością, która się do wzorca nie stosuje. Jak taka kontrola działa i dlaczego dopisanie commita z poprawką jej nie zadowoli, opisuje Rozdział 21.

Wiadomość · część commita, nie etykieta

Co warto w niej napisać

Wiadomość ma budowę, którą git traktuje poważnie: pierwsza linia jest tematem, po niej pusta linia, a dalej opis. Nie jest to konwencja towarzyska — git log --oneline, interfejsy przeglądarkowe i komunikaty scalania biorą właśnie tę pierwszą linię, więc jeśli sklei się ją z resztą, wszędzie pojawi się ścięty w połowie akapit.

budowa wiadomoscigdzie ktora czesc trafia
Temat odpowiada na „co”, opis na „dlaczego”. Drugiego nie widać w diffie.

Praktyczna konsekwencja: pisz temat tak, żeby dało się go przeczytać na liście dwudziestu innych. Tryb rozkazujący („Dodaj”, „Popraw”) nie jest kaprysem — pasuje do tego, jak git sam formułuje swoje commity („Merge branch…”, „Revert…”) i pozwala czytać historię jako listę wykonanych operacji.

Opis warto pisać wtedy, gdy jest co napisać. Jeśli zmiana jest oczywista, sam temat wystarcza. Jeśli wybrałeś jedno z dwóch rozwiązań, odrzuciłeś oczywiste podejście albo obszedłeś cudzy błąd — to jest dokładnie ta wiedza, której za pół roku nikt nie odtworzy z kodu, łącznie z Tobą.

Z praktyki

Wyrób sobie nawyk czytania git status jako dwóch osobnych list, a nie jednej ściany tekstu. Górna odpowiada na pytanie „co zacommituję”, dolna — „co mi zostanie po commicie”. Kiedy obie są takie, jak chcesz, commit jest tylko formalnością.

Jeśli wpisujesz wiadomość w edytorze, a nie przez -m, pamiętaj, że pusta wiadomość przerywa commit. To najprostszy sposób, żeby wycofać się z commita, który zacząłeś przez pomyłkę.

Słowniczek
staging
Dodawanie treści do indeksu. Po polsku bywa „przygotowanie” — w praktyce mówi się „dodać do commita”.
hunk
Fragment diffa: kilka zmienionych linii z kontekstem. Jednostka, którą operuje add -p.
commit -a
Skrót: dodaj wszystkie śledzone zmiany i zbuduj commit. Pomija pliki nieśledzone.
atomowy commit
Commit zawierający jedną zmianę z jednym powodem, dający się wycofać w całości.
Co dalej

Skoro add decyduje, co wchodzi, to wypada wiedzieć, co git w ogóle bierze pod uwagę. Następny rozdział jest o plikach, których nie chcesz w repozytorium — i o tym, dlaczego .gitignore tak często „nie działa”.
