TL;DR
  • Upstream to nie ustawienie serwera, tylko dwie linijki w lokalnej konfiguracji: z jakim zdalnym repozytorium i z jaką gałęzią skojarzona jest ta gałąź.

Start · trzy komendy i jedna decyzja

Gałąź funkcyjna od zera

Zakładanie gałęzi to jedna komenda, ale poprzedza ją decyzja, o której łatwo zapomnieć: od czego ją odbijasz. Gałąź powstaje tam, gdzie stoi HEAD, więc jeśli stoisz na starym stanie mastera, gałąź odziedziczy tę starość.

nowa gałąźod aktualnego stanu, nie od swojego
git switch master
git pull
git switch -c ABC-1234_wyszukiwarka
Switched to a new branch 'ABC-1234_wyszukiwarka'

Trzy komendy. Drugą pomija się najczęściej i to ona kosztuje najwięcej.

switch -c to skrót na dwie rzeczy naraz: utwórz ref i przypnij do niego HEAD. Nic poza tym się nie dzieje — żadnego commita, żadnej zmiany plików, bo nowa gałąź wskazuje dokładnie ten sam commit co poprzednia.

Pytanie „od czego odbić” ma zwykle oczywistą odpowiedź — od aktualnego stanu gałęzi głównej — ale bywają wyjątki warte świadomej decyzji. Poprawka do wydania odbija się od gałęzi wydaniowej, nie od głównej, bo inaczej niesie ze sobą wszystko, co od tamtego wydania zdążyło wejść. Praca budująca na cudzej, jeszcze niescalonej gałęzi odbija się od niej — i wtedy trzeba pamiętać, że po jej przepisaniu Twoja gałąź zostanie zawieszona w próżni.

Nazwa gałęzi jest prawie dowolna, ale prawie zawsze podlega konwencji zespołu — najczęściej z numerem zgłoszenia na początku. Warto się jej trzymać nie z uprzejmości, tylko dlatego, że po tygodniu git branch potrafi wypisać kilkanaście pozycji i wtedy poprawka2 nie mówi nic. Ukośnik w nazwie nie jest znakiem specjalnym — refs/heads/feature/coś to po prostu podkatalog w .git/refs.

Upstream · dwie linijki, które zmieniają wszystko

Co robi -u przy pierwszym pushu

Świeża gałąź jest lokalna i git nie ma pojęcia, gdzie miałaby trafić. Pierwszy push podaje się więc z -u, a git zapisuje przy okazji skojarzenie. Można je zobaczyć, bo to zwykła konfiguracja:

git config --local --listpo git push -u origin ABC-1234
remote.origin.url=../origin.git
remote.origin.fetch=+refs/heads/*:refs/remotes/origin/*
branch.ABC-1234_wyszukiwarka.remote=origin
branch.ABC-1234_wyszukiwarka.merge=refs/heads/ABC-1234_wyszukiwarka

Dwie podświetlone linie to cały upstream. Nic z tego nie jest zapisane po stronie serwera.

Od tej chwili git push i git pull bez argumentów wiedzą, co robić, a git status ma z czym porównywać. Zobaczysz to także w wypisie gałęzi:

git branch -vvskojarzenia widoczne wprost
git branch -vv
* ABC-1234_wyszukiwarka 407463b [origin/ABC-1234_wyszukiwarka] Dodaj wyszukiwarke
  master                f0bae61 [origin/master] Konfiguracja projektu
skad push wie dokadtrzy warstwy konfiguracji
Upstream jest notatką lokalną. Dlatego świeży klon ma ją dla gałęzi domyślnej, a dla Twoich nowych — nie.
Konsekwencje · co z tego wynika

„Gałąź śledzi zdalną” znaczy mniej, niż brzmi

Słowo „śledzi” sugeruje aktywne pilnowanie, jakby git obserwował serwer. Nic takiego się nie dzieje. Skojarzenie mówi tylko, z czym porównywać i dokąd wysyłać, a porównanie robi się względem lokalnej kopii stanu serwera — czyli refa origin/*, o którym jest następny rozdział.

Wynikają stąd dwie rzeczy praktyczne. Po pierwsze, git status może z pełnym przekonaniem twierdzić, że jesteś „up to date”, będąc o tydzień w tyle — bo porównuje z tym, co ostatnio pobrałeś. Po drugie, upstream da się ustawić i zmienić w każdej chwili, także bez pushowania: git branch --set-upstream-to=origin/inna.

Jest jeszcze trzecia, bardziej praktyczna niż obie poprzednie: skoro to zwykła konfiguracja, to przy zmianie nazwy gałęzi po stronie serwera trzeba ją poprawić u siebie ręcznie. Objawem jest push, który nagle chce utworzyć nową gałąź zdalną zamiast zaktualizować istniejącą.

Skąd biorą się gałęzie zdalne

Jedna linijka konfiguracji, cała mapa

W wypisie konfiguracji była linia, którą łatwo przeoczyć, a która odpowiada za całe nazewnictwo origin/*:

remote.origin.fetchreguła odwzorowania
+refs/heads/*:refs/remotes/origin/*

Po lewej to, co jest na serwerze. Po prawej — gdzie ma wylądować u Ciebie.

refspec przy fetchugwiazdka po obu stronach
Refy zdalne to kopie w osobnej przestrzeni nazw — dlatego nie kolidują z Twoimi gałęziami.

Ta osobna przestrzeń nazw ma praktyczny sens: możesz mieć własną gałąź master i jednocześnie widzieć origin/master, bez żadnej kolizji. Możesz też mieć więcej niż jedno zdalne repozytorium — origin, upstream, cudzy widelec — i każde z nich dostanie swój własny katalog refów.

Wynika stąd jeszcze jedno: refy zdalne są tylko do odczytu. Nie da się na nich commitować ani ich przestawiać — aktualizuje je wyłącznie rozmowa z serwerem. Jeśli chcesz pracować na gałęzi, którą ktoś wypchnął, musisz założyć własną gałąź lokalną wskazującą na to samo miejsce; robi to git switch ABC-1234, który przy braku takiej gałęzi lokalnej tworzy ją i od razu ustawia upstream.

Z praktyki

Jeśli irytuje Cię pamiętanie o -u, ustaw git config --global push.autoSetupRemote true. Wtedy pierwszy push nowej gałęzi sam zapisze skojarzenie, z domyślnym zdalnym repozytorium i tą samą nazwą.

Przy sprzątaniu po scalonych gałęziach przydaje się git fetch --prune: usuwa lokalne refy origin/* wskazujące na gałęzie, których na serwerze już nie ma. Bez tego lista gałęzi zdalnych rośnie w nieskończoność i po pół roku nie da się w niej niczego znaleźć.

Słowniczek
upstream
Gałąź zdalna skojarzona z lokalną, zapisana w .git/config.
remote
Nazwany adres zdalnego repozytorium. origin to tylko konwencjonalna nazwa pierwszego z nich.
tracking branch
Lokalna gałąź mająca ustawiony upstream. „Śledzenie” oznacza wyłącznie skojarzenie.
prune
Usunięcie lokalnych refów zdalnych, którym nie odpowiada już nic na serwerze.
Co dalej

Padło już kilka razy zdanie, że origin/master jest lokalny. Następny rozdział bierze je na poważnie — i pokazuje, że połowa mylących liczb w interfejsach bierze się właśnie stąd.
