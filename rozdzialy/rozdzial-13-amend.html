amend: dlaczego poprawka literówki buduje nowy commit

Wiadomość commita nie jest polem, które da się poprawić — jest częścią commita. Dlatego „popraw opis” zawsze oznacza zbudowanie commita od nowa.

TL;DR
  • Wiadomość commita nie jest polem w bazie danych, które dałoby się poprawić. Jest częścią commita, a adres commita liczy się z jego treści — więc inna wiadomość to z definicji inny commit.
  • --amend nie edytuje niczego. Buduje nowy obiekt z tym samym rodzicem co poprzedni i przestawia na niego karteczkę gałęzi. Stary commit zostaje na dysku, tylko przestaje być wskazywany.
  • Jeśli poprawiona gałąź była już wypchnięta, zwykły push zostanie odrzucony — i słusznie, bo Twój nowy commit nie jest potomkiem tego z serwera, tylko jego rodzeństwem.
Punkt wyjścia · literówka, której nie widać

Trzy znaki, które nie dojechały ze schowka

Wklejasz przygotowaną wiadomość commita do okna w IDE, klikasz, idziesz dalej. Dopiero po chwili orientujesz się, że w historii jest odaj wyszukiwarke zamiast [ABC-1234] Dodaj wyszukiwarke. Prefiks i pierwsza litera zostały w schowku.

To wygląda na najdrobniejszą możliwą usterkę: trzy znaki w opisie, kod bez zmian, testy przechodzą. Pierwszy odruch — dopisać drugi commit z poprawką albo „wejść i poprawić opis”. Żadne z tych dwóch nie działa, i to nie dlatego, że git jest niewygodny, tylko dlatego, że nie ma czegoś takiego jak edycja commita.

Mechanizm · adres wynika z treści

    
Dlaczego opisu nie da się podmienić w miejscu


    
Zajrzyj do commita tym, czym git go widzi. git cat-file -p wypisuje surową treść obiektu:


    

      
git cat-file -p HEADsurowa treść obiektu


git cat-file -p HEAD
tree d09fcdce979ee552ec3fcb677a2cd0361f846902
parent f0bae61e149afb77a3b0413aed840734e313783f
author Ty <ty@example.com> 1788807845 +0200
committer Ty <ty@example.com> 1788807846 +0200

[ABC-1234] Dodaj wyszukiwarke

    

    
To jest cały commit. Pięć linii i wiadomość — nic więcej w nim nie ma.


    
Wiadomość leży w tym samym obiekcie co wskaźnik na drzewo plików i wskaźnik na rodzica. A SHA commita to skrót policzony z tego całego tekstu. Zmiana jednego znaku w ostatniej linii zmienia skrót tak samo, jak zmiana zawartości pliku — bo dla funkcji skrótu to jest po prostu inne wejście.


    

      
commit.hashco wchodzi do adresu

      
      
Wiadomość jest jednym z czterech wejść skrótu. Nie ma sposobu, żeby ją wymienić i zachować adres.

    


    
Stąd wniosek, który warto zapamiętać raz na zawsze: w gicie nie istnieje operacja „edytuj commit”. Wszystko, co brzmi jak edycja — --amend, rebase, squash — sprowadza się do jednego i tego samego: zbuduj nowe obiekty i przestaw wskaźnik gałęzi.

  


  

    
Skutek uboczny · commit, który stracił karteczkę

    
Stary commit nie zniknął


    
Po amendzie git log pokazuje jeden commit i wygląda to na podmianę. W rzeczywistości na dysku leżą dwa obiekty, a jeden z nich przestał być przez cokolwiek wskazywany. Git ma na to nazwę i potrafi go pokazać:


    

      
git reflogruchy HEAD, nie historia gałęzi


git reflog -3
407463b HEAD@{0}: commit (amend): [ABC-1234] Dodaj wyszukiwarke
7fbdb3e HEAD@{1}: commit: odaj wyszukiwarke
f0bae61 HEAD@{2}: checkout: moving from master to ABC-1234_wyszukiwarka

git fsck --lost-found
dangling commit 7fbdb3e42b459418a4f6c25ef75e83b7c342bf5b

    

    
„dangling” znaczy dokładnie tyle: obiekt istnieje, ale nie prowadzi do niego żaden ref.


    
To jest powód, dla którego nieudany amend nie jest katastrofą. Dopóki stary skrót widnieje w reflogu — domyślnie około trzydziestu dni — wystarczy git reset --hard 7fbdb3e, żeby wrócić do stanu sprzed poprawki. Reflog dostaje osobny rozdział; tutaj wystarczy wiedzieć, że siatka istnieje.

  


  

    
Konsekwencja · push przestaje przechodzić

    
Rodzeństwo, nie następca


    
Zwykły push przyjmuje aktualizację tylko wtedy, gdy commit, który wysyłasz, jest potomkiem tego, który leży na serwerze. Wtedy nic nie ginie: ref przesuwa się do przodu po istniejącym łańcuchu. Po amendzie ten warunek jest złamany — nowy i stary commit mają tego samego rodzica i żaden nie pochodzi od drugiego.


    

      
git pushgałąź wypchnięta przed amendem


git rev-list --left-right --count HEAD...@{upstream}
1       1

git push
To ../origin.git
 ! [rejected]        ABC-1234_wyszukiwarka -> ABC-1234_wyszukiwarka (non-fast-forward)
error: failed to push some refs to '../origin.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.

    

    
Pierwsza komenda mówi wszystko: jeden commit u mnie, jeden na serwerze, wspólny rodzic. Gałęzie się rozjechały.


    
Podpowiedź gita jest tu myląca, bo dotyczy najczęstszej przyczyny, a nie Twojej. git pull byłby tu najgorszym z możliwych ruchów: ściągnąłby z powrotem commit z literówką i scalił go z poprawionym, więc w historii wylądowałyby oba. Właściwą odpowiedzią jest git push --force-with-lease — powiedzenie serwerowi, żeby ustawił ref na Twój skrót:


    

      
git push --force-with-leasewynik


git push --force-with-lease
 + 7fbdb3e...407463b ABC-1234_wyszukiwarka -> ABC-1234_wyszukiwarka (forced update)

    


    
Trzy kropki między skrótami zamiast dwóch to nie ozdoba: git sygnalizuje w ten sposób, że aktualizacja nie była przewinięciem do przodu. Wariant --force-with-lease różni się od gołego --force tym, że najpierw sprawdza, czy na serwerze leży to, czego się spodziewasz — jeśli w międzyczasie ktoś tam coś dołożył, odmówi zamiast nadpisać cudzą pracę.


    

      
Kiedy tego nie robić

      
Amend i wymuszony push są bezpieczne na Twojej gałęzi funkcyjnej, której nikt jeszcze nie recenzuje i na której nikt nie oparł swojej pracy. Nie robi się tego na gałęziach chronionych, ani po otwarciu merge requesta — komentarze recenzenta są przypięte do konkretnych skrótów i po przepisaniu historii tracą kotwicę.

    

  


  

    
Z praktyki

    
Amend potrafi przy okazji zrobić dwie rzeczy naraz: podmienić wiadomość i wciągnąć do tego samego commita poprawki, które właśnie dodałeś do indeksu. Jeśli po zbudowaniu commita zauważysz jednocześnie literówkę w opisie i drobny błąd w kodzie, popraw jedno i drugie, zrób git add, a potem jeden --amend. W historii zostanie jeden czysty commit, bez śladu w stylu „fix typo”.

    
Zanim wymusisz push, upewnij się, że poprawiasz to, co myślisz: git log -1 --pretty=%s wypisze samą wiadomość ostatniego commita. To dwie sekundy, a chroni przed wymuszeniem pusha stanu, którego nie sprawdziłeś.

  


  

    
Słowniczek

    

      
amend
Zbudowanie nowego commita w miejsce ostatniego, z tym samym rodzicem, i przestawienie na niego gałęzi. Nie jest edycją.

      
dangling commit
Obiekt, do którego nie prowadzi już żaden ref. Nadal jest na dysku i nadal da się do niego wrócić.

      
non-fast-forward
Odmowa serwera wynikająca z tego, że wysyłany commit nie jest potomkiem tego, który tam leży.

      
--force-with-lease
Wymuszony push z warunkiem: przejdzie tylko wtedy, gdy zdalny ref jest dokładnie tam, gdzie się go spodziewasz.

    

  


  

    
Co dalej

    
Amend jest najprostszym przypadkiem przepisywania historii — dotyczy jednego commita. Następny rozdział pokazuje tę samą mechanikę zastosowaną do całego ciągu commitów naraz, czyli interaktywny rebase: tam też nic nie jest edytowane, tylko budowane od nowa według listy poleceń.
