Fast-forward i anatomia odrzuconego pusha

Zwykły push przechodzi tylko wtedy, gdy nowy commit jest potomkiem tego, który leży na serwerze. Cała reszta komunikatu o odrzuceniu to szczegóły tego jednego zdania.

TL;DR
  • Zwykły push przechodzi tylko wtedy, gdy commit leżący na serwerze jest przodkiem tego, który wysyłasz. Wtedy ref przesuwa się wzdłuż istniejącego łańcucha i nic nie ginie.
  • Odmowa non-fast-forward znaczy dokładnie jedno: rozjechaliście się. Ty masz commity, których nie ma serwer, a serwer ma takie, których nie masz Ty.
  • Podpowiedź, którą git dopisuje do odmowy, dotyczy najczęstszej przyczyny, a nie zawsze Twojej. Zanim ją wykonasz, sprawdź jedną komendą, po której stronie co leży.
Warunek · jedno zdanie, cały mechanizm

Przewinięcie do przodu

Serwer nie zna Twoich intencji. Kiedy prosisz go o zmianę wartości refa, ma do dyspozycji jedno pytanie, na które da się odpowiedzieć bez zgadywania: czy to, co u mnie leży, jest przodkiem tego, co przysyłasz?

Jeśli tak, to znaczy, że nowa wartość zawiera w sobie starą — cała dotychczasowa historia jest częścią nowej. Przesunięcie refa niczego nie usuwa, więc git zgadza się bez pytania. To jest fast-forward: przewinięcie wskaźnika po istniejącym łańcuchu.

dwa przypadkizgoda i odmowa
Ten sam wskaźnik, ta sama komenda. Różni je wyłącznie kształt grafu.

Jeśli nie, to obie wersje są rodzeństwem, a przestawienie refa oznaczałoby, że commity serwera przestają być przez cokolwiek wskazywane. Git odmawia — nie dlatego, że to niemożliwe, tylko dlatego, że nie ma podstaw, by uznać to za Twoją intencję.

Diagnoza · po której stronie co leży

    
Jedna komenda zamiast zgadywania


    
Komunikat odmowy mówi, że push się nie udał, ale nie mówi, dlaczego akurat u Ciebie. Przyczyny są dwie i wymagają zupełnie różnych reakcji: albo ktoś dołożył commity na serwerze, albo Ty przepisałeś historię u siebie. Rozróżnia je jedna komenda:


    

      
git rev-list --left-right --count HEAD...@{upstream}trzy kropki, nie dwie


git rev-list --left-right --count HEAD...@{upstream}
1       1        ← 1 commit u mnie, 1 na serwerze, wspolny rodzic

git status -sb
## ABC-1234...origin/ABC-1234 [ahead 1, behind 1]

    

    
Ta sama informacja w dwóch postaciach. „ahead” to Twoje commity, „behind” to te, których nie masz.


    
Czytaj to tak:


    
    
      
  • ahead N, behind 0 — jesteś do przodu, push przejdzie. Jeśli nie przechodzi, problem jest gdzie indziej: uprawnienia, hook, chroniona gałąź.
    • 
      
  • ahead 0, behind N — masz zaległości, ale nic własnego. Wystarczy git pull i push nie będzie potrzebny.
    • 
      
  • ahead N, behind M — rozjazd. Trzeba zdecydować, co zrobić z obiema stronami: scalić, przepisać albo wymusić.
    • 
    


    
Szczególnie warto zwrócić uwagę na trzeci przypadek z M równym liczbie commitów, które właśnie przepisałeś. Jeżeli po amendzie widzisz 1 1, a wiesz, że nikt inny na tej gałęzi nie pracuje, to „behind 1” nie oznacza cudzej pracy — to Twój własny commit sprzed poprawki. Wtedy odpowiedzią jest wymuszony push, a nie pull.

  


  

    
Pułapka · podpowiedź, która bywa myląca

    
Dlaczego git pull nie zawsze jest odpowiedzią


    
Do odmowy git dopisuje podpowiedź: „Updates were rejected because the tip of your current branch is behind its remote counterpart. If you want to integrate the remote changes, use git pull before pushing again.” Dla najczęstszej przyczyny — kolega wypchnął coś przed Tobą — jest to rada trafna.


    
Jeśli jednak rozjazd wziął się z Twojego amendu albo rebase'u, git pull jest ruchem najgorszym z możliwych. Ściągnie z powrotem commit sprzed poprawki i scali go z poprawionym, więc w historii wylądują oba: ten z literówką i ten bez. Dokładnie to, czego chciałeś uniknąć, plus commit scalający.


    
Reguła jest prosta i warto ją mieć odruchowo: zanim wykonasz podpowiedź, sprawdź, czy „behind” to cudza praca, czy Twoja własna sprzed przepisania. Pierwsza wymaga pobrania. Druga wymaga wymuszenia — o czym jest następny rozdział.

  


  

    
Domyślnie · gdzie właściwie leci ten push

    
Co znaczy samo git push


    
Push bez argumentów wygląda na komendę bez treści, a w rzeczywistości niesie komplet informacji — tyle że wziętych z konfiguracji. Rozwinięta wersja tego, co się dzieje, to git push origin ABC-1234:ABC-1234: nazwa zdalnego repozytorium, źródło i cel.


    
Zapis ze dwukropkiem nazywa się refspec i mówi: weź mój ref po lewej i ustaw nim ref po prawej. Dwie strony mogą się różnić, choć w praktyce prawie nigdy tego nie robisz. Skąd git bierze te wartości, gdy ich nie podajesz, opisuje Rozdział 8 — to jest właśnie upstream zapisany w lokalnej konfiguracji.


    
Warto zdawać sobie z tego sprawę z jednego powodu: kiedy komunikat mówi ABC-1234 -> ABC-1234, nie powtarza się bez sensu. Po lewej jest to, co wysyłasz, po prawej — co ma zostać ustawione po drugiej stronie. Ta sama para pojawia się w każdej odmowie i w każdym potwierdzeniu, więc warto ją czytać jako parę, a nie jako ozdobnik.

  


  

    
Z praktyki

    
W interfejsie IDE odmowa zwykle pojawia się jako okienko z propozycją „Merge”, „Rebase” albo „Force push”. Wybór w tym okienku jest dokładnie tą samą decyzją co powyżej, tylko postawioną wtedy, kiedy najtrudniej ją podjąć — w pośpiechu i bez patrzenia na graf. Warto zamknąć okienko, sprawdzić git status -sb, i dopiero potem wrócić.

    
Jeśli po pobraniu chcesz uniknąć commita scalającego przy zwykłym nadrabianiu zaległości, ustaw sobie git config --global pull.rebase true. Wtedy pull dokłada Twoje commity na szczyt pobranych zamiast je scalać. Więcej w Dodatku B.

  


  

    
Słowniczek

    

      
fast-forward
Przesunięcie refa wzdłuż istniejącego łańcucha. Nic nie powstaje i nic nie przestaje być wskazywane.

      
non-fast-forward
Odmowa: wysyłany commit nie jest potomkiem tego, który leży po drugiej stronie.

      
upstream, @{upstream}
Gałąź zdalna skojarzona z bieżącą. Skrót @{u} działa wszędzie tam, gdzie można podać commit.

      
ahead / behind
Ile commitów masz ponad wspólny punkt i ile ma ich druga strona.
