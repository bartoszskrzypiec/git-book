Poświadczenia i transport: SSH, HTTPS, credential helper

Spora część „błędów gita” to w rzeczywistości brakujący program w PATH albo klucz, którego agent nie widzi. Warto umieć je odróżnić w dziesięć sekund.

TL;DR
  • Git sam nie przechowuje haseł. Robi to osobny program — credential helper — wskazany w konfiguracji. Jeśli go nie ma w PATH, git prosi o hasło albo odmawia.
  • Dwa transporty: SSH używa pary kluczy i agenta, HTTPS — nazwy użytkownika i tokenu. To dwa niezależne światy, a ten sam serwer zwykle udostępnia oba.
  • Sporo „błędów gita” to w rzeczywistości problemy stacji: brakujący program, klucz niewidoczny dla agenta, zepsuty wpis w konfiguracji. Warto umieć je odróżnić w kilkanaście sekund.
Kto trzyma hasło

Git deleguje to na zewnątrz

Kiedy git potrzebuje poświadczeń, nie sięga do żadnej własnej bazy. Uruchamia program o nazwie git-credential-<coś>, gdzie „coś” pochodzi z konfiguracji, i pyta go o dane. Program ten może je trzymać w magazynie systemowym, w pliku albo w pamięci przez kilka minut.

brakujący helperkomunikat, który wygląda na błąd gita
git push
git: 'credential-manager' is not a git command.
fatal: could not read Username for 'https://gitlab.przyklad': No such device or address

Pierwsza linia mówi wszystko: git szukał programu i go nie znalazł. Druga to tylko konsekwencja.

Ten komunikat wprowadza w błąd, bo brzmi jak problem z serwerem albo z uprawnieniami. W rzeczywistości nie doszło nawet do próby połączenia: zabrakło programu na tej konkretnej maszynie. Ten sam projekt, ten sam użytkownik i to samo repozytorium będą działać na innej stacji bez żadnej zmiany.

Diagnoza zajmuje dwie komendy. Najpierw sprawdzasz, jaki helper jest ustawiony i skąd pochodzi ustawienie, a potem, czy taki program w ogóle istnieje:

diagnostykadwie komendy
git config --show-origin credential.helper
file:C:/Program Files/Git/etc/gitconfig   manager

git credential-manager --version
# jesli tu jest blad, to jest cala przyczyna
Dwa transporty · i dwa zestawy problemów

SSH kontra HTTPS

dwie drogi do tego samego repozytoriumrozne mechanizmy
Adres w remote.origin.url decyduje, którym z dwóch światów posługuje się to repozytorium.

Wybór transportu jest zapisany w adresie i można go zmienić w każdej chwili: git remote set-url origin .... To jest pierwsza rzecz warta sprawdzenia, gdy jedno repozytorium działa, a drugie nie — bardzo często różnią się właśnie tym.

SSH ma jedną cechę, która myli najczęściej: klucz może istnieć na dysku, a mimo to nie być używany, bo agent go nie załadował. Objawem jest prośba o hasło do klucza przy każdej operacji albo odmowa dostępu mimo poprawnie wgranego klucza publicznego. Komenda ssh-add -l wypisuje, co agent aktualnie widzi, i zwykle rozstrzyga sprawę w sekundę.

HTTPS psuje się inaczej: tokeny wygasają. Komunikat o odmowie dostępu przy niezmienionej konfiguracji, na repozytorium, które działało wczoraj, prawie zawsze oznacza wygasły token — a nie zmianę uprawnień.

Odróżnianie · kod czy stacja

Trzy pytania, które oszczędzają godzinę

Warto mieć gotowy odruch na sytuację, w której coś nie działa, a nie wiadomo, po czyjej stronie leży problem. Trzy pytania wystarczają, żeby to rozstrzygnąć.

  • Czy ten sam problem występuje na innym repozytorium? Jeśli tak — to konfiguracja stacji, nie projekt.
  • Czy komunikat wspomina o czymś spoza gita? Nazwa programu, ścieżka, PATH, agent, token, certyfikat — to wszystko są rzeczy środowiska.
  • Czy poprzedziło to jakiekolwiek połączenie? Odmowa, która przyszła natychmiast, zwykle nie zdążyła dotknąć serwera.

Czwarte pytanie, wykraczające poza samego gita, brzmi: czy coś się na tej stacji ostatnio zmieniło. Aktualizacja systemu, nowa wersja narzędzia, zmiana zasad w firmie — wszystko to potrafi usunąć albo podmienić program, na którym git polega, bez żadnego związku z Twoim projektem.

Ten sam schemat myślenia wraca w piątej części tej książki, w znacznie bardziej podstępnej postaci — tam problemem nie będą poświadczenia, tylko wersje modułów, a błąd będzie wyglądał jak zwykły błąd w kodzie.

Warto też pamiętać, że konfiguracja gita ma trzy poziomy: systemowy, użytkownika i repozytorium, przy czym bardziej szczegółowy wygrywa. git config --list --show-origin pokazuje wszystkie naraz razem z plikami, z których pochodzą — i to jest jedyna komenda, która odpowiada na pytanie „skąd to ustawienie się wzięło”.

Konfiguracja · trzy poziomy, jeden wynik

Skąd bierze się dane ustawienie

Wiele niewytłumaczalnych zachowań gita to po prostu ustawienie, o którym się nie wie. Konfiguracja składa się z trzech warstw i wygrywa najbardziej szczegółowa — repozytorium bije użytkownika, użytkownik bije system.

trzy poziomy konfiguracjiwygrywa najwezszy
Trzy pliki, jedna wynikowa wartość. Bez --show-origin nie da się zgadnąć, który zadecydował.

Najczęstszym praktycznym przypadkiem jest adres użytkownika: globalnie masz swój prywatny, a w repozytorium służbowym potrzebujesz służbowego. Wystarczy wtedy git config user.email ... bez --global, wykonane w tym repozytorium — i tylko ono będzie miało inną wartość.

Drugim częstym przypadkiem jest ustawienie odziedziczone po kimś: skopiowana konfiguracja, instrukcja z sieci sprzed lat, wpis dodany przez narzędzie. Objawem bywa git zachowujący się inaczej niż u kolegi mimo tej samej wersji. git config --list --show-origin rozstrzyga to w jednej komendzie, bo pokazuje nie tylko wartości, ale i pliki, z których pochodzą.

Warto też wiedzieć, że część ustawień dotyczy konkretnych adresów. Zapis [url "..."] insteadOf potrafi po cichu podmieniać adres repozytorium przy każdej operacji — bardzo przydatne w firmowych konfiguracjach i bardzo mylące, kiedy się o nim nie wie.

Z praktyki

Jeśli operacja z terminala nie działa, a ta sama z IDE tak (albo odwrotnie), to prawie na pewno różnica w środowisku, a nie w gicie. IDE bywa uruchamiane z innym PATH, innym agentem SSH, czasem nawet z inną instalacją gita. Sprawdź git --version i git config --show-origin credential.helper w obu miejscach — jeśli wyniki się różnią, masz odpowiedź.

Przy pierwszej konfiguracji nowej stacji warto od razu ustawić user.name i user.email. Git pozwoli commitować bez nich, wpisując zgadniętą wartość, a taki commit potrafi potem nie przejść przez kontrolę serwera albo nie zostać przypisany do Twojego konta.

Słowniczek
credential helper
Zewnętrzny program przechowujący poświadczenia. Git tylko go woła.
agent SSH
Program trzymający odblokowane klucze w pamięci, żeby nie podawać hasła przy każdej operacji.
token dostępu
Hasło jednorazowego przeznaczenia, generowane w interfejsie serwera. Zwykle ma datę ważności.
--show-origin
Przełącznik pokazujący, z którego pliku pochodzi każde ustawienie.
