rebase -i: reword, squash, fixup, drop

Interaktywny rebase to lista poleceń, którą git wykonuje od góry. Nic w niej nie edytuje istniejących commitów — każda linia buduje nowe.

TL;DR
  • Interaktywny rebase to lista poleceń, którą git wykonuje od góry do dołu. Nie edytuje niczego — buduje commity od nowa, jeden po drugim.
  • Cztery polecenia załatwiają dziewięćdziesiąt procent przypadków: reword (zmień opis), squash i fixup (scal z poprzednim), drop (wyrzuć).
  • Wszystko, co przepiszesz, dostaje nowe skróty — także commity, których w liście nie tknąłeś, jeśli leżą powyżej zmienionego. Dlatego rebase kończy się tak samo jak amend: gałąź trzeba wypchnąć siłą.
Punkt wyjścia · lista, nie edytor

Co się otwiera po rebase -i

Wpisujesz git rebase -i HEAD~2 i otwiera się plik. Nie jest to edytor commitów ani formularz — to zwykły plik tekstowy z listą poleceń do wykonania:

git rebase -i HEAD~2plik zadań, skrócony
pick a5a32af # Commit 2
pick e72b434 # Commit 3

# Rebase e0cffc1..e72b434 onto e0cffc1 (2 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's log message
# d, drop <commit> = remove commit

Zamykasz plik, a git wykonuje to, co w nim zostawiłeś. Pusty plik oznacza „nie rób nic” — i tak się przerywa rebase, którego się rozmyśliłeś.

Zwróć uwagę na kolejność: od najstarszego do najnowszego, czyli odwrotnie niż w git log. To najczęstsze źródło pomyłki przy pierwszych próbach, bo „scal z poprzednim” znaczy „z tym, który jest wyżej na liście”, a nie „z tym, który jest wyżej w logu”.

Argument HEAD~2 nie mówi „przepisz dwa commity”, tylko „zacznij od tego miejsca”. To punkt, od którego historia zostanie zbudowana od nowa; wszystko poniżej niego pozostaje nietknięte. Dlatego jeśli chcesz poprawić commit sprzed pięciu innych, musisz podać HEAD~5 — i wszystkie pięć zostanie przebudowanych, choć zmieniasz jeden.

Mechanizm · to jest ciąg amendów

Git odtwarza commity, jeden po drugim

Rebase robi dokładnie to samo co Rozdział 13, tylko wielokrotnie. Ustawia się na commicie bazowym, bierze pierwszy commit z listy, buduje jego nową kopię na bieżącym szczycie, przechodzi do następnego i powtarza.

Rebase buduje kopie, nie przenosi oryginałów

Jeden krok. Porównaj skrót przed i po.

Stary commit zostaje na rysunku przygaszony — nadal jest na dysku i nadal jest w reflogu.

Lista jest wejściem, commity są wyjściem. Nic po lewej nie zostaje zmodyfikowane.

    


    
Ponieważ każda kopia ma innego rodzica niż oryginał, ma też inny skrót — a skoro tak, to każdy commit powyżej też musi zostać zbudowany od nowa, bo w jego treści siedzi skrót rodzica. Stąd zdanie, które warto zapamiętać: rebase przepisuje wszystko od punktu startowego w górę, niezależnie od tego, ile commitów naprawdę zmieniasz.


    
Konflikty w trakcie rebase'u nie są awarią, tylko zwykłą konsekwencją tego, że commit budowany jest na innej podstawie niż powstał. Git zatrzymuje się, prosi o rozstrzygnięcie i czeka na git rebase --continue. Zawsze dostępne jest też git rebase --abort, które przywraca stan sprzed rozpoczęcia — dosłownie, bo gałąź wraca na stary skrót, a wszystkie zbudowane po drodze kopie zostają bez wskaźnika.

  


  

    
Zastosowania · po co to komu

    
Cztery polecenia, które wystarczą

Usunięcie linii z listy działa tak samo jak drop — polecenie istnieje po to, żeby decyzja była widoczna.


    
Najczęstszy realny scenariusz wygląda tak: gałąź ma cztery commity, z czego dwa to „poprawka po recenzji” i „literówka”. Przed scaleniem chcesz, żeby została jedna czysta zmiana. Ustawiasz fixup przy tych dwóch, zamykasz plik i gałąź ma dwa commity zamiast czterech.


    
Drugi częsty powód to porządek przed recenzją. Historia, w której widać „dodaj funkcję”, „napraw test”, „napraw test naprawdę”, opowiada o Twoim popołudniu, a nie o zmianie w projekcie. Recenzent czyta ją commit po commicie, więc każdy zbędny krok kosztuje go uwagę. Rebase pozwala oddać to, co powinno zostać w historii, zamiast tego, co się po drodze wydarzyło.


    
Jest na to jeszcze wygodniejsza droga, o której mało kto wie: przy commitowaniu poprawki użyj git commit --fixup <sha>, a potem git rebase -i --autosquash. Git sam ustawi te commity we właściwych miejscach z poleceniem fixup — nie musisz przestawiać niczego ręcznie.


    

      
Zanim zaczniesz

      
Rebase przepisuje historię, więc obowiązują te same granice co przy amendzie: własna gałąź funkcyjna — tak; gałąź chroniona albo taka, na której ktoś oparł swoją pracę — nie. Jeśli nie jesteś pewien, gdzie stoisz, Rozdział 17 zawiera listę pytań, na które trzeba odpowiedzieć twierdząco, zanim wymusisz push.

    

  


  

    
Z praktyki

    
Zanim uruchomisz rebase na gałęzi, na której Ci zależy, zanotuj sobie gdzieś bieżący skrót: git rev-parse HEAD. Nie dlatego, że rebase jest niebezpieczny — jest odwracalny — tylko dlatego, że w razie pomyłki nie będziesz musiał niczego szukać w reflogu. git reset --hard <ten skrót> przywraca stan sprzed operacji.

    
Jeśli rebase zatrzymał się na konflikcie i nie wiesz, w którym miejscu listy jesteś, git status odpowie: podaje numer kroku, nazwę commita i podpowiada trzy dostępne wyjścia (continue, skip, abort).

  


  

    
Słowniczek

    

      
todo list
Plik z listą poleceń rebase'u. Wykonywany od góry, czyli od najstarszego commita.

      
squash / fixup
Scalenie commita z poprzednim. Różnią się tylko losem wiadomości scalanego commita.

      
autosquash
Tryb, w którym git sam układa commity oznaczone jako fixup! i squash! we właściwych miejscach listy.

      
--abort
Przerwanie rebase'u i powrót do stanu sprzed. Zawsze dostępne, dopóki operacja trwa.

    

  


  

    
Co dalej

    
Amend i rebase budują nowe commity. Następny rozdział zajmuje się komendami, które budują mniej albo nic — i porządkuje trzy słowa, które w rozmowie brzmią tak samo: reset, restore i revert.
