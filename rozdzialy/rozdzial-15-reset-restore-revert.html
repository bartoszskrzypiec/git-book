reset, restore, revert — tabela decyzyjna

Trzy komendy, które w potocznym języku nazywa się tak samo: „cofnij”. Różnią się tym, które z trzech drzew ruszają — i czy zostawiają ślad w historii.

TL;DR
  • Trzy komendy, które po polsku nazywa się tak samo — „cofnij” — robią trzy różne rzeczy. Różnią się tym, które z trzech drzew ruszają.
  • reset przesuwa gałąź. restore zmienia pliki. revert dopisuje nowy commit odwracający zmianę.
  • Kryterium wyboru jest jedno i nie dotyczy techniki: czy ten commit ktoś już widział. Jeśli tak — revert. Jeśli nie — masz wolną rękę.
Uporządkowanie · co która komenda dotyka

Trzy komendy, trzy zasięgi

Wróćmy do rysunku z Rozdziału 1: katalog roboczy, index, HEAD. Każda z trzech komend działa na innym wycinku tego układu i to jest cała różnica między nimi.

zasieg komendktore drzewo rusza sie
Im szersze pole, tym więcej może zginąć. Tylko --hard dotyka niezapisanej pracy.

Kluczowa obserwacja: tylko reset --hard potrafi coś nieodwracalnie stracić, i to nie commity, tylko zmiany, których nigdy nie zacommitowałeś. Commity są bezpieczne, bo zostają w reflogu. Plik, który zmieniłeś i nie dodałeś, nie ma gdzie zostać — nie istnieje żaden obiekt z jego treścią.

Różnicę między trybami widać w statusie od razu. Po reset --soft HEAD~1 zmiana czeka w indeksie, gotowa do ponownego commita, po --mixed leży już tylko na dysku:

git status --shortpo dwóch trybach resetu
git reset --soft HEAD~1 && git status --short
M  plik.txt        ← litera w PIERWSZEJ kolumnie: w indeksie

git reset --mixed HEAD && git status --short
 M plik.txt        ← litera w DRUGIEJ kolumnie: tylko na dysku

Dwie kolumny statusu to dokładnie dwa porównania z Rozdziału 1: index kontra HEAD i katalog kontra index.

Reset · to jest przesunięcie karteczki

Nic nie zostaje usunięte

Nazwa „reset” sugeruje kasowanie i to jest jej największa wada. W rzeczywistości git reset robi to samo, co robi każdy commit — nadpisuje czterdzieści bajtów w pliku gałęzi — tylko wskazuje przy tym wstecz zamiast do przodu.

Skoro reset tylko przesuwa wskaźnik, to działa też w drugą stronę: git reset --hard <stary-skrót> przywraca gałąź dokładnie tam, gdzie była. Cały Rozdział 18 jest o tym, skąd wziąć ten skrót, gdy się go już nie pamięta.

  


  

    
Revert · jedyna opcja, gdy commit wyjechał

    
Historia rosnąca do przodu


    
git revert nie rusza niczego, co już istnieje. Liczy zmianę odwrotną do wskazanego commita i dopisuje ją jako nowy commit na szczycie. Historia się wydłuża, a nie skraca, i widać w niej zarówno błąd, jak i jego wycofanie.


    
Brzmi to jak wersja gorsza — zostaje ślad — ale w jednej sytuacji jest jedyną poprawną. Jeżeli commit trafił już na wspólną gałąź, to ktoś mógł go pobrać. Przesunięcie gałęzi wstecz sprawiłoby, że u niego commit nadal jest, a u Ciebie już nie; przy najbliższym scaleniu wróciłby jak gdyby nigdy nic. Revert nie ma tego problemu, bo nie zmienia przeszłości, tylko dodaje przyszłość, i każdy, kto pobierze zmiany, dostanie także wycofanie.

Kontekst historyczny · skąd tyle nazw

    
Dlaczego istnieje jeszcze checkout


    
Jeśli szukałeś kiedyś w sieci, jak cofnąć zmianę w pliku, prawie na pewno trafiłeś na git checkout -- plik. Ta komenda nadal działa i robi to samo co git restore plik. Warto wiedzieć, dlaczego są dwie.


    
checkout przez lata robił w gicie trzy niezwiązane ze sobą rzeczy: przełączał gałęzie, tworzył nowe i przywracał pliki. Efekt był taki, że jedna literówka w argumencie zmieniała operację nieszkodliwą w taką, która kasuje pracę. W 2019 roku rozdzielono to na dwie komendy o wąskich zakresach: switch zajmuje się gałęziami, restore plikami.


    
Praktyczny wniosek jest taki, że w nowym kodzie i w nowych nawykach warto używać nowej pary, bo trudniej nią zrobić sobie krzywdę. Stary checkout nie zniknie — zbyt wiele instrukcji i skryptów go używa — ale kiedy widzisz go w cudzej odpowiedzi w sieci, przetłumacz sobie od razu, o którą z dwóch operacji chodzi.


    
Przy okazji: żadna z tych komend nie ma nic wspólnego z revert, mimo podobieństwa nazw po polsku. restore działa na plikach i nie zostawia śladu, revert działa na commitach i zostawia ślad celowo.

  


  

    
Z praktyki

    
Najczęstsza pomyłka w tej trójce nie polega na wybraniu złej komendy, tylko na uruchomieniu reset --hard z niezapisanymi zmianami w katalogu roboczym. Commity przetrwają, praca z ostatniej godziny nie. Odruch, który to rozbraja: przed każdym --hard zerknij w git status, a jeśli cokolwiek tam jest — najpierw git stash.

    
Warto też wiedzieć, że reset bez trybu to --mixed. Jeśli w cudzej instrukcji widzisz samo git reset HEAD~1, to znaczy: cofnij gałąź, zostaw pliki w spokoju, wyczyść index.

  


  

    
Słowniczek

    

      
reset --soft / --mixed / --hard
Trzy zasięgi tej samej operacji: sama gałąź, gałąź z indeksem, gałąź z indeksem i plikami.

      
restore
Nowsza komenda do przywracania plików, wydzielona z przeciążonego checkout.

      
revert
Nowy commit z odwrotną zmianą. Jedyny sposób wycofania czegoś, co już wyjechało.

      
HEAD~1
Rodzic bieżącego commita. HEAD~n to n-ty przodek idąc po pierwszych rodzicach.
