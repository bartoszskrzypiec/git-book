Force push: --force, --force-with-lease i granice

Wymuszony push mówi serwerowi: ustaw ten ref na mój SHA, cokolwiek tam leży. Różnica między dwoma wariantami polega na tym, czy najpierw sprawdzasz, co tam leży.

TL;DR
  • Wymuszony push mówi serwerowi: ustaw ten ref na mój skrót, cokolwiek tam leży. Nie scala, nie porównuje, nie pyta.
  • --force-with-lease robi to samo, ale najpierw sprawdza, czy po drugiej stronie jest to, czego się spodziewasz. Jeśli ktoś zdążył coś dołożyć — odmawia z komunikatem stale info.
  • Granica nie jest techniczna, tylko społeczna: wolno nadpisywać to, czego nikt inny nie używa jako punktu odniesienia. Wszystko poza tym jest cudzą sprawą.
Co ta komenda właściwie robi

Bez pytania, bez scalania

Zwykły push prosi o przesunięcie refa i przyjmuje odmowę. Wymuszony push nie prosi — nakazuje. Serwer ustawia wskazaną wartość i tyle; commity, które były tam wcześniej, przestają być przez cokolwiek wskazywane.

Warto od razu zauważyć, czego wymuszony push nie robi. Nie kasuje commitów — one zostają w repozytorium po tamtej stronie, dokładnie tak samo jak stary commit po amendzie zostaje u Ciebie. Nie łączy niczego z niczym. I nie ostrzega przed niczym poza tym, o co sam poprosisz.

W wyniku widać to jako trzy kropki między skrótami i słowo w nawiasie:

git push --force-with-leasegdy wszystko się zgadza
git push --force-with-lease
To ../origin.git
 + 7fbdb3e...407463b  ABC-1234 -> ABC-1234 (forced update)

Przy zwykłym pushu byłyby dwie kropki. Trzy oznaczają: to nie było przewinięcie do przodu.

Ten znak plus na początku linii i te trzy kropki to jedyne miejsce, w którym git informuje, że stało się coś nieodwracalnego dla drugiej strony. Warto je rozpoznawać, bo w oknie IDE zwykle nie widać ich wcale.

Dwa warianty · i dlaczego jeden jest lepszy

--force kontra --force-with-lease

Gołe --force nadpisuje ref bez żadnego warunku. Jeśli w międzyczasie ktoś wypchnął tam swoją pracę, zniknie ona z gałęzi — nie z repozytorium, ale z tego, co ktokolwiek zobaczy — a Ty nie dowiesz się, że w ogóle istniała.

--force-with-lease dokłada jeden warunek: przejdź tylko wtedy, gdy zdalny ref ma dokładnie tę wartość, którą ja u siebie zapamiętałem. To jest ta sama wartość, którą widzisz jako origin/ABC-1234. Jeśli się nie zgadza, znaczy to, że po ostatnim pobraniu coś się tam wydarzyło — więc push zostaje odrzucony:

git push --force-with-leasegdy ktoś zdążył coś wypchnąć
git push --force-with-lease
To ../origin.git
 ! [rejected]        master -> master (stale info)
error: failed to push some refs

stale info to jedyny komunikat gita, który znaczy: „twoje wyobrażenie o serwerze jest nieaktualne”.

Ten komunikat jest dobrą wiadomością, choć wygląda jak zła. Właśnie uratował cudzą pracę, którą gołe --force nadpisałoby bez słowa. Właściwa reakcja to git fetch, spojrzenie, co przyszło, i dopiero potem decyzja.

co sprawdza leasetrzy wartosci
Warunek dotyczy tego, co pamiętasz o serwerze — dlatego fetch tuż przed wymuszeniem osłabia zabezpieczenie.

Wynika stąd rzecz nieoczywista: odruchowe git fetch tuż przed --force-with-lease psuje sens tego wariantu. Fetch aktualizuje Twoją pamięć o serwerze, więc warunek zaczyna się zgadzać i push przechodzi — łącznie z nadpisaniem tego, co właśnie pobrałeś. Pobieraj, patrz, decyduj; nie pobieraj po to, żeby przestało protestować.

Granica · pięć pytań przed wymuszeniem

Kiedy wolno, a kiedy nie

Technicznie wymusić można prawie zawsze. Pytanie brzmi, kto poza Tobą używa tego refa jako punktu odniesienia — bo dla każdej takiej osoby historia zmieni się pod ręką.

PytanieOdpowiedź, która pozwala
Czy to moja gałąź funkcyjna?Tak. Gałęzie chronione odpadają z definicji.
Czy jest już otwarty merge request?Nie — albo tak, ale nikt jeszcze nie recenzował.
Czy ktoś odbił od niej swoją gałąź?Nie.
Czy ktoś ją u siebie pobrał?Nie wiem — i wtedy trzeba zapytać.
Czy mam zapisany stary skrót?Tak, choćby w reflogu.

Cztery pierwsze pytania dotyczą innych ludzi. Tylko ostatnie dotyczy gita.

Dla osoby, która pobrała starą wersję gałęzi, wymuszony push wygląda dokładnie tak, jak wyglądałby dla Ciebie: przy najbliższym pobraniu jej gałąź lokalna i zdalna okażą się rodzeństwem, a git pull zrobi scalenie, wciągając z powrotem commity, które właśnie wyrzuciłeś. Dlatego uprzedzenie zespołu jednym zdaniem jest tańsze niż sprzątanie tego potem.

Trzy miejsca, w których to jest zawsze błąd

Gałęzie chronione (master, main, wydaniowe) — tam serwer i tak odmówi, a jeśli nie odmawia, to konfiguracja jest zepsuta. Gałąź w trakcie recenzji — komentarze przypięte do konkretnych skrótów tracą kotwicę. Gałąź, na której pracuje ktoś jeszcze — nadpisujesz mu punkt odniesienia i jego następny pull zrobi bałagan, którego on nie zrozumie.

Ta sama gałąź, dwie odpowiedzi serwera

W widgecie wszystko dzieje się na jednym ekranie, więc trudno się pomylić co do skutków. W rzeczywistości drugiego panelu nie widać — jedyne, co masz, to trzy linie komunikatu. Dlatego warto wyrobić sobie odruch czytania ich uważnie: plus i trzy kropki oznaczają, że po drugiej stronie coś przestało istnieć dla wszystkich poza tym, kto zna skrót.

  


  

    
Z praktyki

    
Ustaw sobie git config --global alias.pushf 'push --force-with-lease' i używaj wyłącznie tego skrótu. Gołe --force jest wtedy o kilka znaków dalej niż wariant bezpieczny, a to wystarczy, żeby nie sięgać po nie odruchowo.

    
W IDE sprawdź raz, którego wariantu używa przycisk „Force push”. Część narzędzi wysyła --force-with-lease, część gołe --force, a różnica ujawnia się dopiero w dniu, w którym ktoś inny akurat pracował na tej samej gałęzi.

  


  

    
Słowniczek

    

      
--force
Ustaw zdalny ref na moją wartość bez żadnego warunku.

      
--force-with-lease
To samo, ale tylko jeśli zdalny ref ma wartość, którą pamiętam z ostatniego pobrania.

      
stale info
Odmowa wariantu z lease: po drugiej stronie leży coś innego, niż myślisz.

      
forced update
Potwierdzenie w wyniku pusha, z plusem i trzema kropkami. Oznacza, że coś przestało być wskazywane.

    

  


  

    
Co dalej

    
Trzy poprzednie rozdziały kończyły się tym samym zdaniem: „stary commit zostaje w reflogu”. Następny rozdział pokazuje, czym ten reflog jest, jak długo działa i jak z niego skorzystać w chwili, w której wydaje się, że praca zniknęła.
