Rozdział 7 / Codzienna praca

.gitignore, śledzenie i wyjmowanie plików

.gitignore nie działa wstecz. Plik raz zacommitowany jest śledzony niezależnie od wzorców — i to jest najczęstsze „dlaczego to dalej widać”.

TL;DR
  • .gitignore działa tylko na pliki nieśledzone. Plik raz zacommitowany jest śledzony na zawsze, niezależnie od wzorców.
  • Stąd najczęstsze „.gitignore nie działa”: plik wszedł do repozytorium wcześniej. Lekarstwem jest git rm --cached, które usuwa go z indeksu, zostawiając na dysku.
  • Ignorowanie nie jest zakazem. git add -f dodaje plik mimo wzorca — i właśnie tak ignorowane pliki najczęściej trafiają do historii.
Reguła · jedna, i wyjaśnia wszystko

Ignorowanie dotyczy tylko nieśledzonych

Git dzieli pliki w katalogu na dwie grupy: te, o których wie (śledzone — są w indeksie), i całą resztę. .gitignore mówi wyłącznie o tej reszcie: „nie wspominaj mi o tych plikach w statusie i nie dodawaj ich przez add .”.

Plik, który jest już śledzony, tej reguły nie dotyczy. Git wie o nim, więc pokazuje jego zmiany, choćby pasował do dziesięciu wzorców naraz:

plik śledzony mimo wzorcacache.tmp jest w .gitignore
cat .gitignore
cache.tmp

git status --short
 M cache.tmp        ← sledzony, wiec ignorowanie go nie dotyczy

Wzorzec jest, plik jest w statusie. To nie usterka, tylko dokładnie ta jedna reguła.

decyzja gitaprzy kazdym pliku
Wzorzec jest brany pod uwagę dopiero w drugim pytaniu. Do pierwszego nie ma nic do powiedzenia.
Naprawa · wyjąć plik z indeksu

git rm --cached

Skoro problemem jest obecność w indeksie, rozwiązaniem jest usunięcie go stamtąd — bez usuwania pliku z dysku. Dokładnie to robi git rm --cached:

git rm --cachedplik zostaje, śledzenie znika
git rm --cached cache.tmp
rm 'cache.tmp'

git status --short
D  cache.tmp        ← usuniecie CZEKA w indeksie, plik nadal jest na dysku

Po commicie git przestanie o nim wiedzieć i dopiero wtedy wzorzec zacznie działać.

Warto zrozumieć, co znaczy ten commit. Jest w nim usunięcie pliku — dla każdego, kto go pobierze, plik zniknie z katalogu roboczego. Przy pliku z lokalną konfiguracją bywa to niemiła niespodzianka, więc taki commit wypada opisać wprost i uprzedzić zespół.

Jest jeszcze druga część prawdy, mniej przyjemna: plik zostaje w historii. Wszystkie commity, w których był, nadal go zawierają, więc każdy klon nadal ma jego treść. Dla śmieciowego pliku tymczasowego to bez znaczenia. Dla pliku z hasłem — przeciwnie: usunięcie z indeksu nie jest wtedy żadnym zabezpieczeniem, a jedyną poprawną reakcją jest unieważnienie tego hasła.

Trzy miejsca na reguły

PlikZakresDla czego
.gitignore w repowszyscy, jest w commitachWyniki budowania, katalogi cache — rzeczy wspólne dla projektu
.git/info/excludetylko Ty, tylko to repoTwoje pliki robocze, których nikt inny nie ma

Reguła kciuka: co dotyczy projektu — do repo; co dotyczy Ciebie — poza repo.

Ta różnica bywa źródłem drobnych, ale męczących sporów. Pliki katalogu .idea/ albo .vscode/ nie są plikami projektu, tylko Twojego narzędzia, więc ich miejsce jest w konfiguracji globalnej — chyba że zespół świadomie zdecydował, że część z nich chce współdzielić.

Dwie rzeczy o samych wzorcach warto zapamiętać, bo powodują najwięcej zamieszania. Ukośnik na końcu (build/) oznacza wyłącznie katalog. Wykrzyknik na początku odwraca regułę (!wazny.log), ale nie zadziała, jeśli wykluczony jest cały katalog nadrzędny — git nie wchodzi do zignorowanego katalogu, więc nie ma szansy zobaczyć wyjątku w środku.

trzy listy wzorcowi ich zasieg
Wybór listy to pytanie o zasięg, nie o wygodę.

Gdy wzorzec nie działa i nie wiadomo dlaczego, git odpowie wprost: git check-ignore -v plik wypisuje regułę, plik i numer linii, która zdecydowała. To jedna komenda zamiast czytania trzech list wzorców.

Przypadek szczególny · pliki, które i tak trafiają

Ignorowanie to nie zakaz

Warto zauważyć asymetrię, która zaskakuje przy pierwszym zetknięciu. Ignorowany plik nie pojawia się w statusie i nie zostanie dodany przez git add . — ale podany wprost z -f wejdzie bez oporu:

git addna pliku pasującym do wzorca
git add cache.tmp
The following paths are ignored by one of your .gitignore files:
cache.tmp
hint: Use -f if you really want to add them.

Git ostrzega i podpowiada obejście w tej samej wiadomości. Ostrzeżenie jest jedynym zabezpieczeniem.

To jest projekt świadomy: .gitignore ma odsiewać szum, a nie egzekwować politykę. Jeżeli czegoś naprawdę nie wolno wpuścić do repozytorium — bo to poświadczenie albo plik z hasłem — właściwym miejscem na taką kontrolę jest hook, a nie lista wzorców. Rozdział 20 pokazuje, gdzie takie kontrole żyją i dlaczego te po stronie serwera są jedynymi, których nie da się pominąć.

Druga rzecz, o którą warto zapytać wcześniej niż później: czy ten plik w ogóle powinien być w gicie. Duże pliki binarne — tekstury, cache, wyniki symulacji — zostają w historii na zawsze i w każdym klonie, bo git nie potrafi ich zapisać różnicowo. Odpowiedzią bywa osobny mechanizm przechowywania dużych plików albo trzymanie ich poza repozytorium; ważne, żeby decyzję podjąć przed pierwszym commitem, a nie po roku.

Z praktyki

Zakładając nowy projekt, dodaj .gitignore zanim zrobisz pierwszy commit. Kolejność odwrotna to najczęstszy sposób, w jaki katalog z wynikami budowania trafia do repozytorium — a potem trzeba go stamtąd wyjmować osobnym commitem i tłumaczyć zespołowi, dlaczego pliki zniknęły im z dysku.

Jeśli w statusie jest kilkadziesiąt linii ??, potraktuj to jako sygnał, a nie tło. Status, w którym nie da się jednym rzutem oka zobaczyć swojej pracy, przestaje pełnić swoją funkcję — a to on jest w tej książce najczęściej polecanym odruchem.

Co dalej

Repozytorium masz uporządkowane. Następny rozdział zakłada gałąź funkcyjną od zera i wyjaśnia, skąd git push bez argumentów wie, dokąd właściwie ma wysłać — bo nie wie tego z serwera.
