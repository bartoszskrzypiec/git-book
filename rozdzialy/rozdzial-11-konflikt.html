Konflikt: co git pokazuje i jak to czytać

Konflikt nie jest awarią. Jest miejscem, w którym git odmawia zgadywania — a znaczniki w pliku mówią dokładnie, czyja wersja jest która.

TL;DR
  • Konflikt nie jest awarią. To miejsce, w którym git odmawia zgadywania, bo obie strony zmieniły to samo.
  • Markery w pliku dzielą go na dwie wersje: nad linią ======= jest Twoja, pod nią cudza. Nazwa gałęzi po prawej mówi, czyja.
  • ours i theirs znaczą co innego przy merge'u niż przy rebasie. Przy rebasie są zamienione, bo to Ty jesteś odtwarzany na cudzej podstawie.
Skąd się bierze · trzy wersje, nie dwie

Git porównuje trzy rzeczy naraz

Scalając, git nie zestawia dwóch wersji pliku, tylko trzy: Twoją, cudzą i wspólnego przodka. Dopiero to pozwala mu rozstrzygnąć większość przypadków samodzielnie. Jeśli linia zmieniła się tylko u Ciebie, bierze Twoją. Jeśli tylko u drugiej strony — jej. Konflikt zgłasza wtedy i tylko wtedy, gdy obie strony zmieniły to samo miejsce inaczej.

scalanie trojstronneprzodek jako rozjemca
Bez wspólnego przodka każda różnica byłaby konfliktem. To on sprawia, że scalanie zwykle przechodzi samo.

Warto to wiedzieć, bo tłumaczy, dlaczego konflikty pojawiają się rzadziej, niż można by się spodziewać, i dlaczego czasem pojawiają się tam, gdzie „przecież nic nie zmieniałem” — na przykład po zmianie wcięć w całym pliku, gdy z punktu widzenia gita zmieniły się wszystkie linie.

Markery · jak to czytać

Co git wpisuje do pliku

Przy konflikcie git zostawia plik na dysku w postaci zawierającej obie wersje, oddzielone trzema liniami znaków:

plik po konflikcietrzy linie markerów
<<<<<<< HEAD
wersja B
=======
wersja A
>>>>>>> galaz

Nad ======= jest to, co masz. Pod — to, co przychodzi. Etykiety po bokach mówią, skąd każda wersja pochodzi.

Komunikat w terminalu wygląda tak samo za każdym razem i warto go czytać do końca, bo zawiera nazwę pliku:

git mergekomunikat
git merge galaz
Auto-merging f.txt
CONFLICT (content): Merge conflict in f.txt
Automatic merge failed; fix conflicts and then commit the result.

git status --short
UU f.txt          ← UU: zmienione po obu stronach

Rozwiązanie konfliktu polega na zostawieniu w pliku tego, co ma tam być — i usunięciu wszystkich trzech linii markerów. Nie musisz wybierać jednej ze stron: równie dobrze możesz napisać trzecią wersję, która łączy obie. Git nie sprawdza, co wybrałeś; sprawdza tylko, czy powiedziałeś, że skończyłeś.

Warto przy tym pamiętać, że plik z markerami jest zwykłym plikiem na dysku i nic nie stoi na przeszkodzie, żeby otworzyć go w edytorze. Narzędzia graficzne do scalania pokazują to samo w trzech kolumnach i bywają wygodne przy dużych konfliktach, ale nie robią nic, czego nie dałoby się zrobić ręcznie — a przy jednym czy dwóch miejscach ich uruchamianie trwa dłużej niż poprawka.

A mówi się to przez git add — tę samą komendę co zawsze. Dodanie pliku do indeksu jest tu deklaracją „ten plik jest już rozwiązany”. Potem git merge --continue albo git rebase --continue domyka operację. W obu przypadkach dostępne jest też --abort, wracające do stanu sprzed.

Pułapka · ours i theirs zamieniają się miejscami

Czyja jest „nasza” wersja

Git pozwala rozstrzygnąć konflikt hurtowo: git checkout --ours plik albo --theirs. Nazwy wyglądają na oczywiste i właśnie dlatego są niebezpieczne — ich znaczenie zależy od operacji.

Operacjaours totheirs to
mergegałąź, na której stoiszgałąź, którą scalasz
rebasegałąź, na którą przenosisz (cudza)Twój odtwarzany commit
cherry-pickgałąź bieżącakopiowany commit

Drugi wiersz zaskakuje wszystkich. Wynika z tego, że przy rebasie to Ty jesteś odtwarzany na cudzej podstawie — więc z punktu widzenia gita „nasze” jest to, na czym budujesz.

Praktyczny wniosek: nie ufaj tym nazwom przy rebasie. Zamiast zgadywać, spójrz na markery w pliku — etykieta przy >>>>>>> nazywa konkretny commit albo gałąź, a to jest informacja jednoznaczna. Jeżeli i to nie wystarcza, git log --merge -p plik pokazuje commity z obu stron, które dotknęły tego pliku.

Zapobieganie · konflikt to skutek, nie przyczyna

Skąd biorą się te trudne

Konflikty dzielą się na dwie grupy i warto je rozróżniać, bo wymagają zupełnie różnych reakcji.

dwa rodzajei co z nimi robic
Pierwszy to koszt narzędzia. Drugi to informacja, że ktoś pracował nad tym samym.

Konflikt techniczny bierze się z tego, że git porównuje linie tekstu, a nie znaczenie kodu. Przeniesienie funkcji o dwadzieścia linii wyżej jest dla niego usunięciem i dodaniem, więc każda cudza zmiana w tej okolicy stanie się konfliktem. Tu odpowiedzią jest po prostu uważne rozstrzygnięcie — i unikanie commitów, które przy okazji przeformatowują pół pliku.

Konflikt rzeczywisty jest cenniejszy, choć mniej przyjemny: mówi, że dwie osoby niezależnie ruszyły to samo. Rozstrzyganie go w pojedynkę, przez wybranie „swojej” wersji, potrafi po cichu wyrzucić cudzą poprawkę. To jest moment na jedno pytanie zadane autorowi drugiej zmiany, a nie na szybkie --ours.

Częstotliwość konfliktów zależy zresztą nie od gita, tylko od tego, jak długo gałęzie żyją osobno. Gałąź trzydniowa ma ich mało, trzytygodniowa dużo — i to jest właściwa reakcja na powtarzające się konflikty: skracać gałęzie i częściej nadrabiać zaległości, a nie szukać lepszego narzędzia do scalania.

Z praktyki

Najczęstszy błąd przy konflikcie to nie zły wybór wersji, tylko zostawiony marker. Linia ======= albo >>>>>>>, która pojedzie w commicie, psuje plik i zwykle wychodzi dopiero przy uruchomieniu. Zanim zamkniesz konflikt, wyszukaj ciąg <<<<<<< w całym repozytorium.

Konflikt w pliku binarnym nie ma markerów — nie da się ich wstawić do obrazka. Git zgłasza go osobno i wybór sprowadza się do jednej z dwóch wersji: git checkout --ours plik albo --theirs, z uwagą na pułapkę z tabeli powyżej.

Słowniczek
scalanie trójstronne
Porównanie dwóch wersji z ich wspólnym przodkiem. Dzięki niemu większość różnic rozstrzyga się sama.
markery konfliktu
Trzy linie wstawiane do pliku: początek, granica i koniec. Muszą zniknąć przed commitem.
UU
Kod w statusie: plik zmieniony po obu stronach i nierozwiązany.
--continue / --abort
Domknięcie przerwanej operacji albo powrót do stanu sprzed niej.
