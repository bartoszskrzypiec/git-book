reflog: siatka bezpieczeństwa, o której się zapomina

Commit, do którego nie prowadzi żadna gałąź, nie znika. Leży na dysku, a git pamięta, gdzie był HEAD — domyślnie przez trzydzieści dni.

TL;DR
  • Reflog to dziennik ruchów HEAD i gałęzi — zupełnie osobna rzecz niż historia commitów. Zapisuje każde przestawienie wskaźnika, także takie, po którym commit stracił gałąź.
  • Dzięki temu prawie nic w gicie nie ginie. Nieudany rebase, przypadkowy reset --hard, nadpisany amend — wszystkie zostawiają w reflogu skrót, na który da się wrócić.
  • Dwa ograniczenia: reflog jest wyłącznie lokalny i ma termin ważności (domyślnie około trzydziestu dni dla wpisów osiągalnych, dziewięćdziesiąt dla reszty).
Czym to jest · nie historia, tylko dziennik

Zapis tego, gdzie bywał HEAD

git log odpowiada na pytanie „jak powstał ten commit” — idzie po wskaźnikach rodziców i pokazuje historię zawartą w commicie. git reflog odpowiada na zupełnie inne pytanie: „co ja właściwie robiłem”. Jest listą kolejnych wartości, jakie przyjmował HEAD, w porządku czasowym.

git reflogpo amendzie i przełączeniu gałęzi
git reflog -4
407463b HEAD@{0}: commit (amend): [ABC-1234] Dodaj wyszukiwarke
7fbdb3e HEAD@{1}: commit: odaj wyszukiwarke
f0bae61 HEAD@{2}: checkout: moving from master to ABC-1234
f0bae61 HEAD@{3}: commit (initial): Konfiguracja projektu

Wpis HEAD@{1} to commit, którego git log już nie pokaże — nie ma do niego żadnej gałęzi.

Zwróć uwagę na trzy rzeczy w tym wypisie. Po pierwsze, każda linia niesie skrót — a skrót wystarcza, żeby wrócić. Po drugie, git dopisuje przy każdym wpisie, co go spowodowało: commit, checkout, reset, rebase. Po trzecie, ten sam skrót może się powtórzyć, bo przełączenie gałęzi jest ruchem HEAD, choć nie tworzy niczego nowego.

log kontra reflogdwa rozne przejscia
Ten sam moment w repozytorium, dwa różne sposoby przejścia. Tylko jeden pokazuje porzucony commit.

Ta różnica tłumaczy, dlaczego reflog bywa niewidoczny w interfejsach graficznych. Panel historii w IDE rysuje graf commitów, czyli robi to samo co log — a porzucony commit z definicji nie leży w tym grafie. Bywa, że dostęp do reflogu jest w menu pod nazwą w rodzaju „Recent operations”, ale równie często nie ma go wcale i wtedy jedynym wyjściem jest terminal.

Zapis HEAD@{n} działa wszędzie tam, gdzie można podać commit. git show HEAD@{2}, git diff HEAD@{5}, git reset --hard HEAD@{1} — wszystkie są poprawne. Jest też wariant czasowy: HEAD@{2.days.ago} albo HEAD@{yesterday}.

Zastosowanie · powrót po nieudanej operacji

Dwie komendy, żeby cofnąć wszystko

Cały ratunek sprowadza się do dwóch kroków: znajdź w reflogu skrót sprzed operacji, przestaw na niego gałąź. Widget pokazuje ten drugi krok — zwróć uwagę, że nie jest to żadna specjalna komenda naprawcza, tylko zwykły reset z Rozdziału 15.

Praca „zniknęła” i wróciła

Dwa kroki: reset o dwa commity wstecz, potem powrót na skrót z reflogu.

Ten widget potrzebuje JavaScriptu Rozdział jest kompletny bez niego — obie komendy są w tekście obok. 

      
Po pierwszym kroku commity nie znikają z rysunku — bledną. To jest dokładnie ta różnica, którą reflog pozwala odwrócić.

    


    
W praktyce wygląda to tak. Zrobiłeś rebase, wynik jest nie do poznania, chcesz wrócić. Wpisujesz git reflog, szukasz ostatniego wpisu sprzed rebase'u — będzie tuż nad linią z rebase (start) — i wykonujesz git reset --hard na jego skrót. Gałąź wraca dokładnie tam, gdzie była, razem ze wszystkimi commitami.


    
Jest też skrót dla przypadku najczęstszego: każda gałąź ma własny reflog. git reflog ABC-1234 pokazuje ruchy tylko tej gałęzi, a ABC-1234@{1} oznacza jej poprzednią wartość. Po nieudanej operacji na jednej gałęzi to zwykle najkrótsza droga: git reset --hard ABC-1234@{1}.

  


  

    
Granice · czego reflog nie zrobi

    
Lokalny i z terminem ważności


    
Reflog jest wyłącznie Twój. Nie jest wysyłany przy pushu, nie przychodzi przy klonowaniu, nie ma go w świeżym klonie repozytorium. Serwer prowadzi własny, ale nie masz do niego dostępu zwykłymi komendami — więc jeśli praca zniknęła u Ciebie, ratunek jest na Twoim dysku albo nigdzie.


    
Ma też termin ważności. Wpisy wygasają — domyślnie po trzydziestu dniach dla commitów nadal osiągalnych i po dziewięćdziesięciu dla porzuconych — a sprzątanie (git gc) usuwa wtedy obiekty, do których nic już nie prowadzi. W codziennej pracy to wieczność, ale przy powrocie do repozytorium po pół roku reflog będzie miał niewiele do zaoferowania.


    
Jest wreszcie jedna rzecz, której reflog nie obejmuje, i warto ją znać, bo to najczęstsza realna strata: zmiany, które nigdy nie były commitem. Reflog zapisuje ruchy wskaźników, a wskaźnik może wskazywać tylko na obiekt. Plik zmieniony w edytorze i wyrzucony przez reset --hard nigdy nie stał się obiektem, więc nie ma czego przywracać. To jest jedyne miejsce w całej tej książce, w którym praca naprawdę przepada.


    
Wynika stąd jedna praktyczna zasada, wbrew pozorom nietrywialna: jeśli coś poszło nie tak, nie klonuj repozytorium od nowa. Świeży klon wygląda na czysty start, ale przy okazji zostawia za sobą jedyny egzemplarz reflogu, w którym są Twoje porzucone commity. Napraw najpierw to, co masz.


    
Gdy reflog nie wystarcza, zostaje jeszcze git fsck --lost-found, które wypisuje wszystkie obiekty nieosiągalne z żadnego refa. Jest to narzędzie ostatniej szansy — wypis bywa długi i bez opisów — ale jeżeli commit istnieje, znajdzie się tam.

  


  

    
Z praktyki

    
Najlepszy moment na spojrzenie w reflog to nie chwila paniki, tylko pięć minut spokoju. Uruchom git reflog na repozytorium, w którym pracowałeś przez ostatni tydzień, i przeczytaj kilkanaście linii. Zobaczysz swoją własną pracę opisaną komendami gita — i następnym razem, kiedy coś pójdzie nie tak, będziesz wiedział, czego szukać zamiast czytać ten wypis pierwszy raz w życiu.

    
Warto też zapamiętać jedno zdanie i powtarzać je sobie w gorszych momentach: dopóki commit powstał, jest na dysku. Nie ma znaczenia, że git log go nie pokazuje, że gałąź zniknęła ani że IDE twierdzi, że nic tam nie ma.

  


  

    
Słowniczek

    

      
reflog
Dziennik kolejnych wartości refa. Osobny dla HEAD i dla każdej gałęzi.

      
HEAD@{n}
Wartość HEAD sprzed n ruchów. Działa jak zwykły skrót commita.

      
gc (garbage collection)
Sprzątanie: pakuje obiekty i usuwa te nieosiągalne, którym minął termin.

      
fsck --lost-found
Wypis obiektów, do których nie prowadzi żaden ref. Ostatnia deska ratunku.
